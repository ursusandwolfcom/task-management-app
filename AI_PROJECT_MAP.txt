3) АДЕКВАТНІСТЬ АРХІТЕКТУРИ
--------------------------------------------------------------------------------
Стек: Java 21, Spring Boot 4.1, JPA, Liquibase (public), PostgreSQL, ddl-auto=validate,
OAuth2 Resource Server (JWT) + cookie/CSRF browser sessions, React workspace + alpha.

Стиль: модульний моноліт (НЕ мікросервіси) — правильно для 1 розробника і спільної БД.

Шари всередині модуля:
  web → application → persistence
  api = публічний контракт між модулями
  domain (task) / core (planning) = без Spring/JPA/HTTP

Дозволені залежності (ArchitectureRulesTest):
  identity ← []
  project  ← identity
  planning ← []  (лише JDK)
  task     ← project, identity, planning (+ майбутні resource, outbox)
  collaboration ← project, task, identity
  workflow ← project, task, collaboration, …
  security ← identity
  alpha    ← planning
  shared   ← []
  workspace← []

Trade-off: суворі `.api` границі vs трохи більше wiring. Вигода — тестування ядра
без Spring і захист від циклів пакетів. Мікросервіси / CQRS / Outbox зараз надлишкові
(Outbox зарезервований у карті модулів на майбутні notification/attachment).


4) ПАТЕРНИ І НАВІЩО
--------------------------------------------------------------------------------
| Патерн                         | Де                         | Навіщо                                      |
|--------------------------------|----------------------------|---------------------------------------------|
| Hexagonal / Ports & Adapters   | *.api + application/persist| Ізоляція домену від HTTP/JPA                |
| Facade (module API)            | *Operations interfaces     | Міжмодульний доступ лише через контракт     |
| Strategy / Policy              | TaskLifecyclePolicy        | Чисті переходи статусів без I/O             |
| Immutable Value Object         | TaskExecution, GraphSnapshot| Безпечні факти + відтворюваність            |
| Kahn topological sort          | PriorityTopologicalSorter  | Детермінований порядок DAG                  |
| Optimistic locking             | @Version / inputRevision   | Конкурентні правки без lost update          |
| Guard / ContentGuard           | ProjectContentGuard SPI    | Project delete блокується наявністю задач   |
| Adapter                        | AlphaController→planning   | Browser прототип без PostgreSQL CRUD        |
| Exception → ProblemDetail      | ApiExceptionHandler        | Стабільні HTTP code + Cache-Control         |
| ArchUnit rules                 | ArchitectureRulesTest      | Регресія границь модулів                    |

Не використовується (і не треба зараз): Saga, Event Sourcing, повний CQRS, мікросервіси.

7) НАВЧАЛЬНІ МАТЕРІАЛИ ПО КОДУ
--------------------------------------------------------------------------------
УРОК A — Чисте ядро графа (30 хв)
  1. GraphSnapshot.of — валідація вузлів/ребер (self/dup/unknown).
  2. PriorityTopologicalSorter — Kahn + PriorityQueue(TaskOrder).
  3. ReadinessCalculator — available/next після executionOrder (цикл завжди ловиться).
  Тест: PlanningOracleTest, ReadinessCalculatorTest.

УРОК B — Lifecycle без БД (20 хв)
  1. TaskLifecyclePolicy.nextStatus — матриця переходів.
  2. TaskExecution — immutable attempts; retry зберігає FAILED attempt.
  Тест: TaskExecutionTest.

УРОК C — Транзакційний контур (45 хв)
  1. ProjectCoordination.lockAndAuthorize під @Transactional.
  2. TaskService.execute: lock → refresh/version → policy → predecessors → persist.
  3. TaskDependencyService: editable successor тільки NOT_STARTED без attempts;
     цикл через sorter на proposed edges.
  Тест: TaskIntegrationTest, TaskDependencyIntegrationTest (integration).

УРОК D — Границі модулів (20 хв)
  Прочитати ArchitectureRulesTest.MODULE_DEPENDENCIES.
  Спробувати «неправильно» імпортувати TaskEntity з collaboration — тест впаде.

УРОК E — Alpha vs Server (15 хв)
  AlphaController будує GraphSnapshot з тіла запиту і кличе той самий core.
  Server TaskPlanningService вантажить знімок під lock, рахує ПІСЛЯ транзакції.
