2) CODE REVIEW VERDICT (S15/S16)
--------------------------------------------------------------------------------
Verdict: S15 baseline can merge; local S16 cleanup is minor.

A modular monolith with clear .api contracts and pure planning.core fits this scale.
The main risk is planned ArchUnit modules (resource/scheduling/attachment/…) without
code yet; these placeholders are not dead code.

Blocker: none on baseline b7990fe.

Major:
1. Server task/graph UI does not yet complete the README MVP scenario (backend exists,
   workspace is partial). This is a product gap, not a backend defect.
2. ProjectDeletionService is a thin pass-through, intentionally reserved as a workflow
   extension point. Keep it until coordinated task/file deletion is introduced.

Minor:
1. Repeated Long.parseLong(jwt.getSubject()) in controllers can use a local actor();
   a shared helper is not required across different modules.
2. CommentService.delete performs scalar lookup + findById after locking, as LabelService
   does. This is deliberate TOCTOU protection rather than dead duplication.

Ideas:
1. Keep TaskProjectAccess and CollaborationAccess separate: their exception contracts differ.
2. Keep page records in each module's .api; do not move them to shared.

Strengths:
1. ArchUnit enforces module dependencies and planning/task.domain independence.
2. Optimistic concurrency separates task.version from project.inputRevision by meaning.
3. JsonFields / PageRequests / NoNul are appropriate shared utilities without business logic.
4. Missing and inaccessible tasks both return TASK_NOT_FOUND to prevent enumeration.

3) ARCHITECTURE ASSESSMENT
--------------------------------------------------------------------------------
Stack: Java 21, Spring Boot 4.1, JPA, Liquibase (public), PostgreSQL, ddl-auto=validate,
OAuth2 Resource Server (JWT) + cookie/CSRF browser sessions, React workspace + alpha.

Style: modular monolith, appropriate for one developer and a shared database.

Module layers:
  web → application → persistence
  api = public inter-module contract
  domain (task) / core (planning) = no Spring/JPA/HTTP

Allowed dependencies in the historical ArchitectureRulesTest:
  identity ← []
  project  ← identity
  planning ← [] (JDK only)
  task     ← project, identity, planning (+ future resource, outbox)
  collaboration ← project, task, identity
  workflow ← project, task, collaboration, …
  security ← identity
  alpha    ← planning
  shared   ← []
  workspace← []

Trade-off: strict .api boundaries require additional wiring but allow core tests
without Spring and prevent package cycles. At the original review point, microservices,
CQRS and Outbox were considered unnecessary; outbox was reserved for future notification/
attachment work. Outbox was subsequently implemented in S24.

4) PATTERNS AND THEIR PURPOSE
--------------------------------------------------------------------------------
| Pattern | Location | Purpose |
|---------|----------|---------|
| Hexagonal / Ports & Adapters | *.api + application/persistence | Isolate domain from HTTP/JPA |
| Facade (module API) | *Operations interfaces | Contract-only access between modules |
| Strategy / Policy | TaskLifecyclePolicy | Pure status transitions without I/O |
| Immutable Value Object | TaskExecution, GraphSnapshot | Safe facts and reproducibility |
| Kahn topological sort | PriorityTopologicalSorter | Deterministic DAG order |
| Optimistic locking | @Version / inputRevision | Concurrent edits without lost updates |
| Guard / ContentGuard | ProjectContentGuard SPI | Prevent deleting a project containing tasks |
| Adapter | AlphaController → planning | Browser prototype without PostgreSQL CRUD |
| Exception → ProblemDetail | ApiExceptionHandler | Stable HTTP codes and Cache-Control |
| ArchUnit rules | ArchitectureRulesTest | Regression checks for module boundaries |

Not used or required at that review point: Saga, Event Sourcing, full CQRS, microservices.

6) AI CHANGE MAP
--------------------------------------------------------------------------------
CHANGE RULES:
1. Feature in an existing module: api → application → persistence → web → tests.
2. New module: add to MODULE_DEPENDENCIES in ArchitectureRulesTest BEFORE importing.
3. Graph algorithms belong ONLY in planning.core; do not copy them to JS (alpha calls the API).
4. Do not expose Entity/Repository across modules; use *.api records/interfaces.
5. task.domain and planning.core have no Spring/JPA/HTTP; ArchUnit enforces this.
6. Never commit .env; docs/ is locally ignored.
7. Branch cycle: sprint/sNN → PR to dev → verify → merge → release PR → main.
8. Concurrency: graph changes use inputRevision; task metadata uses task.version.
9. Foreign/missing resources return identical 404 codes, such as TASK_NOT_FOUND.
10. Alpha profile and loopback: do not mix localStorage IDs with PostgreSQL IDs.

ENTRY POINTS:
  Application: com.example.taskmanagement.TaskManagementAppApplication
  HTTP: /api/** (JWT or cookie+CSRF), /alpha/** (profile), /workspace
  OpenAPI: /v3/api-docs (alpha documentation profile)
  Compose/Docker: compose.yaml, Dockerfile
  Frontend workspace: frontend/ + scripts/build-workspace.mjs
  Migrations: src/main/resources/db/changelog (Liquibase, public tracking schema)

WHERE TO CHANGE WHAT:
  Lifecycle transitions       → task.domain
  DAG order / available / next → planning.core (+ TaskPlanningService adapter)
  Task/dependency CRUD         → task.application + persistence

7) CODE LEARNING MATERIAL
--------------------------------------------------------------------------------
LESSON A — Pure graph core (30 minutes)
  1. GraphSnapshot.of validates nodes/edges (self/duplicate/unknown).
  2. PriorityTopologicalSorter uses Kahn + PriorityQueue(TaskOrder).
  3. ReadinessCalculator computes available/next after executionOrder; cycles are always detected.
  Tests: PlanningOracleTest, ReadinessCalculatorTest.

LESSON B — Lifecycle without a database (20 minutes)
  1. TaskLifecyclePolicy.nextStatus is the transition matrix.
  2. TaskExecution keeps immutable attempts; retry preserves the FAILED attempt.
  Test: TaskExecutionTest.

LESSON C — Transaction boundary (45 minutes)
  1. ProjectCoordination.lockAndAuthorize runs under @Transactional.
  2. TaskService.execute: lock → refresh/version → policy → predecessors → persist.
  3. TaskDependencyService permits editing a successor only when NOT_STARTED without
     attempts; the sorter checks cycles on proposed edges.
  Tests: TaskIntegrationTest, TaskDependencyIntegrationTest (integration).

LESSON D — Module boundaries (20 minutes)
  Read ArchitectureRulesTest.MODULE_DEPENDENCIES.
  Try an invalid TaskEntity import from collaboration: the test should fail.

LESSON E — Alpha versus server (15 minutes)
  AlphaController builds GraphSnapshot from the request and calls the same core.
  Server TaskPlanningService loads a snapshot under lock, then calculates AFTER the transaction.
